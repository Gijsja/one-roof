## Evidence and corrections to the first proposal

1. `UndergroundOperationsState.ChooseTarget` selects smallest reachable non-AccessHub ID, not a nuanced target priority. It can select SupplyDepot, unstaffed or unpowered rooms. Thus claiming existing operational target selection was incorrect; a decoy-room exploit is real in current targeting. Specify new ranked targets: operational exposure-producing OperationsCenter before Communications, then stable room ID. No eligible producer -> no new event, although existing incidents remain valid. Operational means reachable, non-disrupted at eligibility, required staff assigned and HasRequiredUtilities true. Evaluate utility projection once per sample, not per room. Target freezes; losing operation during incident can contain activity but does not erase exposure history or incurred expense.
2. Three120-tick samples span240 elapsed ticks, not360. Use eligibleSinceTick, first observed eligible sample starts timer, fourth consecutive eligible120-tick sample at first+360 opens warning. A failed entry sample resets timer; sampling gives sustained sampled evidence, not proof of every intervening tick. If strict continuity is intended, update boolean eligibility each tick and use samples only for transition decisions; selected contract here uses sampled continuity explicitly.
3. Existing `AdvanceTick` validates target in Corridor but not Inspect. Add existence/reachability checks before inspection charge. Demolition at Inspect currently risks charge against removed room.
4. Stored `_securityStrength` and `_vaultProtection` are refreshed by AdvanceDaily and saved. A policy/room change is therefore not immediately effective. Define current contract response efficacy as next daily operations snapshot; inspector displays effective snapshot and next refresh. New live recalculation is a separate explicitly chosen implementation change, not an inherited guarantee.
5. Security success decreases exposure. It is containment until both recovery thresholds have held; do not equate security>=12 with causal health. Paid disruption deadline is immutable, inspectionTick+1680, even when exposure improves. No overlapping refresh/recharge.
6. All-simulation zero allocation would create a new beta prerequisite. Keep simulation allocation a profiling report. Roadmap's pooled presentation requirement remains relevant; implementors may optimize simulation after measured evidence. Current scrutiny creates strings and route BFS creates arrays/Queue, so blanket zero allocation is currently false.
7. Scale must mean actual constructed above-ground physical floorCount>=30 (not floor occupancy or staffing on every floor) and ResidentCount>=300 throughout accepted interval. Physical floors distinguish undercity. This avoids imposing unrequested density on 30-floor mixed-use design. Current BuildingTopologyState.FloorCount counts floor slabs; verify exclusions for below-ground before consumption.
8. Low demand is not missing data. Zero completed elevator journeys with correctly observed empty cohorts means wait gate Pass with 'No elevator demand', not Unavailable. All-local trips can legitimately pass. Empty routine cohort likewise Pass only when schedule/demand observer was active and counts exactly zero; a missing observer is Unavailable. Housing/wellbeing/population denominator zero cannot pass due scale gate.
9. Current active-trip persistence does not include completed cohorts. Existing callback only handles Outside Food/MoveOut, despite callback parameter's general name. Never use it as routine success metric. Demand suppressed because person has an active trip currently silently returns; observe suppression separately, not as fabricated successful travel.
10. Current household field `DailyEssentialShortfall` is amount, not event count. Gate can directly require amount==0 per household, including partial-day household archives; no need to invent existing shortfall event count.

## Threshold feasibility: standalone recurrence model, not gameplay proof

External pressure .55 corresponds v=.50; relief .46 corresponds v=.40. Expansion decays .02/tick, policy .01/tick. Ordinary brief construction cannot sustain360 ticks by itself, intentional: crackdown requires sustained adversity plus sustained exposure.

Python iteration of this exact recurrence with expansion/policy/readiness=0, initial v=.1, frozen source inputs for1000 ticks:

- inequality=.8, unresolved=.8, wellbeing=.3,0 services -> v=1, first reaches .5 at tick7.
- inequality=1, unresolved=1, wellbeing=0,0 services -> v=1, first reaches .5 at tick5.

These signatures are proposed, not current:

- DailyGateAccumulator.BeginInterval(long day,long startTick), ObserveTick(in DailyMetricSample), ObserveHouseholdClosed(long householdId,long shortfallAmount,bool partialInterval), RecordTowerTransfer(in OperatingTransfer), RecordRoutineDemand(in RoutineDemandOutcome), CloseInterval(long endTick).
- RoutineDemandOutcome: stable trip ID,person ID,purpose,demandTick,submissionTick,deadlineTick,result,completedTick,elevatorWaitTicks. Home/Work/Food/Leisure/Hygiene eligible; MoveOut excluded. Count generated routine demand even when SubmitTrip suppresses due ongoing trip, recording Suppressed failure. Immediate local completion and no-route cancellation recorded. Actual accepted submission tick defines360 deadline; suppressed demand fails immediately.
- Transit observer is independent from outside transaction callback: record Submitted/Completed/Cancelled/Rejected transitions exactly once; callback cannot introduce cash effects. On deadline process completion at that tick first, then timeout, giving inclusive360 behavior. Percentiles nearest-rank ceil(.95*N), N>0. Completed elevator journeys only for wait percentile; queue maximum covers unresolved live waits too. Empty observed demand/wait collection is valid zero-demand Pass.
- CampaignEligibilityState.PublishPending(sample), ObserveCohortOutcome(...), FinalizeEligibleDay(...), ToSaveData/FromSaveData. Supports32 finalized samples,one pending sample; persisted lastFinalizedDay/streak. Process previous pending deadlines before opening another pending day;360<1440 guarantees one completed-day pending maximum, but current day accumulator also exists and must be saved separately.

Clock currently advances before needs/utility/social/wellbeing/scrutiny/operations. Daily boundary then closes household counters, resets them, payroll/outside payroll/credit/rent/business/underground/upkeep/subsidy, arrears/housing, Economy.CompleteDailySettlement, faction/civil/Caretaker/history, then generates/executes transit. Proposed insertion preserves this production order:
1. At upcoming boundary, close OLD tick accumulator for prior half-open interval before assigning new tick samples; first interval missing tick0 initialization is Unavailable, not healthy by default.
2. Capture household previous interval before reset, including archives for departed households. Mark closed sample still pending transit.
3. Open new operating-ledger interval BEFORE scheduled payroll/rent/business/operations transfers, assigning boundary transfers to new day. Current CompleteDailySettlement mixes intra-interval expenses with boundary-opening revenue: do not derive chosen gate from its LastDaily fields without new interval-tagged accumulator.
4. Complete current fixed tick including all crisis phases and transit; observe stock/service/incident metrics with new tick's interval ID=floor(tick/1440). Track within-tick treasury minimum through mutation callbacks; end-of-tick cash alone can miss negative temporary liquidity.
5. Observe transit completions then inclusive-deadline expiry; finalize oldest pending sample exactly once. UI/explanation sees committed immutable projection.

Within settlement shared effects must consume an explicit snapshot: existing Rent/Civil multiplier from prior settled state applies to that boundary cycle; newly evaluated CivilActions applies next cycle. New contracts may change this only with deliberate ordering/replay fixtures. Infrastructure demand sampled from actual projections, not shared mutable presentation state. Event charges enter ledger at their actual tick.

Operating ledger: internal-business payroll is employer->household and outside payroll outside->household; no Tower expense unless Tower pays. Underground PayResidentWages DOES charge Tower via ChargeDailyExpense (wage3 per worker), so include it as operating expense. Rent/tax/contracts Tower revenue; upkeep/supply purchases/subsidies/inspection/underground wages expenses. Credit repayments use actual lender. Construction and salvage are excluded symmetrically from margin, retained in liquidity; refunds must reverse same category. Once-only provenance includes incident/sequence or command transfer ID; conserves counterparties and distinguishes explicit outside sinks. Existing ChargeDailyExpense combines all nonsubsidy expenses under upkeep; new gate categories are adapter metadata, not inferred from string labels.

## Bounded costs and explicit risks

Reuse384-capacity buffers for controlled allocations; rebuild at topology revision or actual path invalidation, not every tick. Target selection O(rooms), staffCount naive O(assignments) per room; cache count projection once per sample. Route history64 scopes each one target; no unbounded snapshots.

Daily accumulator fixed aggregates O(Residents+occupied rooms+active trips) per tick if straightforward implementation; at300 Residents record measured tick cost before accepting. Keep histograms or fixed-bin counters for satisfaction/strain, queue wait and p95 so no full Resident-tick sample list. Inclusive deadline360 permits each unresolved cohort entry expiry tracked without sorted heap when active IDs bounded; define capacity>=real scheduled peak and fail explicitly on overflow, never silently drop samples. Completed trip outcomes aggregate immediately; pending stores only unresolved IDs. Current accumulator and previous pending are two distinct saved objects, even though one pending day.
